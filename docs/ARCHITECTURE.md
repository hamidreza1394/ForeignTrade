# معماری ForeignTrade

## هدف
سامانه‌ای مستقل برای مدیریت بازرگانی خارجی و عملیات واردات، با پشتیبانی از چند Tenant، چند شرکت عملیاتی برای هر Tenant، گزارش‌های تک‌شرکتی و چندشرکتیِ مجاز، و استقرار ابری یا سرور اختصاصی.

## سبک معماری
- Modular Monolith؛ مرزهای ماژولی روشن، بدون Microservices مگر نیاز اثبات‌شده.
- لایه‌های Domain، Application، Infrastructure و Host/API در حدی که پیچیدگی واقعی توجیه کند.
- SQL Server و EF Core برای ماندگاری داده.
- React + TypeScript + Vite + Tailwind + shadcn/ui برای رابط.
- API هم‌مبدأ تا حد امکان؛ cookie امن HttpOnly و Anti-forgery برای عملیات تغییردهنده در مرورگر.
- همه وابستگی‌های UI به‌صورت محلی بسته‌بندی شوند تا برنامه در شبکه محدود/آفلاین به CDN وابسته نباشد.

## مرزهای اصلی
1. **Identity & Access**: کاربران، اعتبارنامه، نشست، نقش، مجوز و عضویت.
2. **Tenant & Company**: مشتری/مرز داده و شرکت‌های عملیاتی.
3. **Operational Period**: دوره کاری/عملیاتی با قواعد مستقل از دوره مالی حسابداری.
4. **Trade/Import**: پرونده‌ها و گردش کار بازرگانی خارجی مطابق پروپوزال.
5. **Documents & Attachments**: فایل، نسخه، هش و دسترسی.
6. **Audit**: رخدادهای قابل ردیابی و تغییرناپذیر در حد نیاز.
7. **Reporting**: گزارش‌های منبع‌دار، کنترل‌شده و خروجی Excel/PDF.
8. **Licensing Integration (future)**: قرارداد سروری مستقل؛ در فاز حاضر غیرفعال.

## جداسازی داده
- Tenant معرف مشتری/مرز امنیتی است.
- Company معرف شخصیت/واحد عملیاتی درون Tenant است.
- رکوردهای شرکت‌محور باید TenantId و CompanyId معتبر داشته باشند.
- همه queryها و commandها باید مجوز کاربر را در سمت سرور کنترل کنند؛ Global Query Filter فقط دفاع تکمیلی است.
- گزارش چندشرکتی باید فهرست شرکت‌های مجاز را از دسترسی معتبر سرور بگیرد، نه از آرایه ارسالی مرورگر.
- محدودیت یکتایی داده‌ها باید دامنه Tenant یا Company را مطابق معنای کسب‌وکار مشخص کند.

## ورود و انتخاب محیط
- ورود با نام کاربری و گذرواژه؛ اعتبارسنجی سمت سرور.
- پس از ورود، شرکت‌ها و دوره‌های قابل دسترس از سرور خوانده شوند.
- هیچ شرکت/دوره قبلی بدون انتخاب صریح کاربر به‌صورت خودکار فعال نشود؛ استثنای ورود مستقیم تنها وقتی مجاز است که سیاست محصول صریحاً آن را تعریف و سرور یکتایی انتخاب مجاز را اثبات کند.
- اگر فقط یک شرکت/دوره وجود دارد، رفتار ورود مستقیم باید در ADR جداگانه و با توجه به تصمیم کارفرما تعیین شود؛ پیش‌فرض فعلی صفحه انتخاب را نشان می‌دهد.
- انتخاب نهایی شرکت و دوره باید در API مجدداً اعتبارسنجی شود.

## دوره
دوره عملیاتی با `FiscalPeriod` حسابداری فرانو یکی نیست. تعریف دقیق دوره، بازه تاریخ، وضعیت‌ها، قابلیت ورود/ثبت/فقط مشاهده و قواعد بستن آن باید از پروپوزال و فرآیندهای واردات استخراج و در دامنه مستقل پیاده‌سازی شود.

## استقرار
یک کدبیس برای ابر و سرور اختصاصی؛ تفاوت‌ها در configuration و deployment profiles. سامانه مرکزی فروشنده/لایسنس در این مخزن یا بسته مشتری ادغام نمی‌شود، مگر تصمیم معماری آینده آن را جداگانه تعریف کند.

## اصول غیرهدف
- Microservices از ابتدا
- اتصال مستقیم React به دیتابیس
- نگهداری رمز یا کلید محرمانه در کلاینت
- وابستگی به CDN
- کپی کامل دیتابیس، migrations یا مدل حسابداری فرانو
